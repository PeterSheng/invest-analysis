## 六步流程

### 1. 定位缺失行
`ls reports/{YYYYMM}/` 里的公司目录 vs 总表对应月份小节的行，差集 = 待补行。新报告的评分/目标价/击球区从各公司 `05-综合裁决.md`（或旧式 `*-四大师综合报告.md`）头部提取。

### 2. 公司名 → 行情代码映射
从目录名/报告正文提取，按市场加前缀：
- A股：`sh6xxxxx` / `sz0xxxxx` / `sz3xxxxx`；港股：`hk0xxxx`（5 位）；美股：`usTICKER`
- ⚠️ BRK.B 用 `usBRK_B`（**不带交易所后缀**，`usBRK_B.N` 反而失败）；FINV 等腾讯字段异常时用 stockanalysis.com 二次确认

### 3. 腾讯批量行情（qt.gtimg.cn）
```python
import urllib.request, socket
socket.setdefaulttimeout(25)
UA = {"User-Agent": "Mozilla/5.0", "Referer": "https://gu.qq.com/"}
req = urllib.request.Request(f"https://qt.gtimg.cn/q={','.join(codes)}", headers=UA)
t = urllib.request.urlopen(req).read().decode("gbk", errors="ignore")
# 每行 v_{code}=...，按 ~ 分隔：
# [1]=名称  [3]=现价  [4]=昨收  [5]=开盘  [30]=时间戳  [32]=涨跌%
```
- ⚠️ **GBK 编码是硬坑**（2026-10-25 名创优品实战二次踩中）：接口返回 GBK 字节。若走 `subprocess.run(["curl",...], capture_output=True, text=True)`，Python 会按 UTF-8 解码直接炸 `'utf-8' codec can't decode byte 0xc9/0xc3`——**curl 路线必须去掉 `text=True`**，对 bytes 手动 `.decode("gbk", errors="ignore")`；或者直接用上面的 urllib 配方（`urlopen(...).read()` 本来就是 bytes，天然免疫）。两个配方都能用，别混搭出第三个。
- 美股批量按 30 个/批分组；A股/港股一批 60+ 也稳
- 时间戳格式随市场不同，都要校验：美股 `2026-10-23 16:00:01`、A股 `20261023161415`、港股 `2026/10/23 16:08:14`——**三者对不上同一交易日 = 数据源过期，重拉**
- 结果缓存到 `/tmp/quotes_{YYYYMMDD}.json` 便于修补漏网代码时增量补拉

### 3.5 增量补行模式（单份新报告整合，区别于全量刷新）

用户说「把最新报告整合进总表」（只补 1-2 行）时，**不要全量重刷 139 行**：

1. **插行位置**：按评分降序定位；**同分按分析日期排**（名创优品重析 2.88/10-25 排在同分卡特彼勒 2.88/10-03 之后）
2. **首轮行联动**：旧轮行加指针「（10 月重析 2.88，见下）」——重析公司两行必须互相可发现
3. **统计区同步**：月份计数 +1；「重析公司（多轮）」序列追加「公司名（旧分→新分）」；同时把重析条目追加进 `references/analyzed-companies-ledger.md`（公司级台账唯一数据源，2026-10 起独立维护——本节旧表述「repo 没有独立台账文件」已过时，两处都要更新）
4. **表头注记**：头部引言补一句增补记录（「10-25 增补名创优品（重析）行，并抽查美团/苹果/卡特彼勒与原表一致」）
5. **现价列不全量刷新的替代验证**：非交易日（周日）拉价 = 最新收盘就是上周五，原表现价列仍有效；**抽 3 只与原表比对**（美团/苹果/卡特彼勒三市场各一），全吻合 → 原列不动，只填新行的现价。有吻合失败才升级为全量刷新
6. **双市场上市（ADR+港股）**：新行现价列两个都拉、都写（`$10.04（ADR）/19.87 HKD`）——报告正文锚哪个市场就放哪个在前；两边时间戳必须同一收盘日

### 4. 写入与校验门（本会话核心教训）
写入后、commit 前**强制两道门**：
1. **行结构**：逐行数 `|`，每行必须恰好 6 个（数据 5 列 + 分隔）；修正过百事可乐 5→6 列的先例
2. **完整性 grep**：全文件 `None`、`⚠` 必须为 0 才准提交——**映射表 ≠ 拉取清单**是本会话真实事故：映射做了 115+ 只，但拼行情 URL 时漏了 5 只美股（PYPL/NFLX/MNSO/NET 及初版 PayPal），表里留下 "None" 占位，靠 assert 拦下。防法：写完表后用映射清单反查每行现价列非空，而不是信任拉取脚本"应该都拉到了"

### 5. 可疑价格先验证再"修"
现价与击球区严重背离 ≠ 数据错：
- **滔搏 hk06110 报 1.005 HKD**（目标区 4.50-5.00）看似坏数据，但腾讯 [1]名称=滔搏、[4]昨收 0.940、[5]开盘 0.945 全部自洽 → 运动零售真实崩盘，照实写入
- **蜜雪 hk02097 报 166.70**（报告时 ~254）同样为真实下跌
- 验证三件套 = 名称[1] + 昨收[4] + 开盘[5]；三者自洽就接受，并在回复的「异动警示」里向用户点破
- 真正的坏数据特征：名称不符、昨收/开盘缺失、时间戳过期

### 6. 推送
走 SKILL.md「推送关键约束」（execute_code + subprocess、fetch-first 时 pull --rebase、回报 commit hash）。

## 回复用户的三段式输出（2026-10-25 用户认可格式）

1. **新增整合表**：本次补入的报告 | 评分 | 目标价/击球区 | 现价
2. **击球区实时核对**：已进入/贴线标的表（现价 vs 区间，标「刚入区」「区间内」「贴线上方」）——这是用户要这张表的真正目的，最有行动价值的一节
3. **异动警示**：现价偏离报告基准 >5% 的标的 + 一句话归因（跌入悲观情景、破位、越过建仓区上沿等）

## 陷阱速查

| 陷阱 | 正确做法 |
|------|----------|
| `subprocess.run(curl, text=True)` 拉腾讯行情直接 UnicodeDecodeError | qt.gtimg.cn 是 GBK：curl 路线去掉 `text=True` 后 `.decode("gbk", errors="ignore")`，或直接用 urllib 配方（bytes 天然免疫） |
| 单行整合任务做全量刷新 | 走 §3.5 增量补行：插行+首轮行指针+统计区+表头注记+3 只抽查代替全刷 |
| 重析行插入后旧轮行无指针 | 首轮行尾加「（N 月重析 X.XX，见下）」，两行互相可发现 |
| 映射清单 ≠ 拉取清单，漏拉留 None | 提交前 grep None/⚠ 必须为 0；用映射清单反查每行现价非空 |
| 可疑低价直接当坏数据"修掉" | 名称+昨收+开盘三件套验证，自洽即真实（滔搏 1.005 实战） |
| BRK.B 带交易所后缀拉不到 | `usBRK_B` 无后缀 |
| 列头日期不随刷价更新 | 「现价（MM-DD收盘）」日期与本次拉取收盘日一致 |
| 美股一批拉 100+ 只 | 30 只/批分组，防超时/截断 |
| 只报价格不报"落区状态" | 击球区标的必须判读：入区/贴线/越界，单独成节 |
